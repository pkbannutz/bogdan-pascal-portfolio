The original audit was mainly static; this second pass confirms some issues on the deployed site and finds several overlooked opportunities.

## Final host and staging checks (live)

- **POSITIVE:** `https://www.bogdanpascal.com/` resolved to canonical host `https://bogdanpascal.com/` in the browser scraper. `http://bogdanpascal.com/` also resolved to `https://bogdanpascal.com/`. No host-split problem was observed in these two checks. The scraper follows redirects and did **not** expose intermediate HTTP 301/302 codes, so the precise status chain should still be inspected with a header-level tool if necessary.
- **STAGING:** `/filmmaker/v2/` and `/filmmaker/v3/services/colour-grading/` both returned HTTP 200. Source files contain explicit noindex, which is appropriate for preview isolation, but **noindex does not make those previews private**. V2 README explicitly says direct access is public; consider protected staging or removing stale previews from production after they are no longer needed. This is a visibility/privacy decision, not proof they are indexed by Google.
- **LEGACY:** Accessing `/filmmaker/services/on-set/` landed on `/filmmaker/services/dop/` in a browser-based scrape. Source uses meta refresh and `location.replace`, not a confirmed server-side 301. That is acceptable as fallback on GitHub Pages but less clean than a true server redirect if hosting later changes.

## The additional 10 angles investigated

### Pass 11: Actual live crawl, not just a repository inventory (OVERALL)
- Firecrawl crawl from `https://bogdanpascal.com/`, bounded to 50 URLs / depth 5, with preview exclusions and sitemap discovery skipped.
- It returned **35 production pages, all HTTP 200**. Those 35 correspond to root (1), athlete (1), filmmaker landing (1), filmmaker about (1), contact (1), services index (1), five active service pages (5), 23 projects (23), equipment (1).
- Separately fetched root `robots.txt` and `sitemap.xml`, both returned **404** from GitHub Pages.
- **Still unknown:** Google indexation, server HTTP caching policy, redirects for `www` and HTTP, CDN performance by country and user's real mobile connection.
- **Action:** After sitemap publication, verify with Search Console and real HTTP status checks. Keep preview paths out of sitemap but accessible to crawlers that must read noindex.

### Pass 12: Browser network request audit (FILMMAKER)
- Real browser navigation test at `/filmmaker/` recorded approx 57ms TTFB from request start, 300ms DOMContentLoaded, and 420ms page load. **One unthrottled browser session is not a field speed report.**
- Network resource inspection observed all **23 distinct portfolio JPGs** fetched, totaling about **4.83 MB encoded image payload** (before any browser cache benefit). Some hover/transition images are also declared as CSS backgrounds.
- The JS inserts **six hero background layers immediately**, each with a different still image. These use images also found in the thumbnail set, so do not simply add six files to the count or double-count transferred bytes.
- Root-cause hypothesis: CSS background images on `.mk` layers cause downloads outside the viewport even when underlying `img loading="lazy"` attributes exist; browser evidence supports the outcome but an uncached DevTools network trace is needed to prove request initiators individually.
- **Change proposal:** Display the same tiles but use CSS mask/text overlay without a second background, or conditionally assign background-image only as tile approaches viewport. Lazy load future hero images just before crossfade and preload only the first required hero still. Keep showreel film look and hover effects.
- **Acceptance:** Cold 390px mobile trace should not fetch all 23 images before scrolling; compare total transfer, LCP/INP/CLS and visual fidelity. No arbitrary PageSpeed score claimed.

### Pass 13: Mobile usability and conversion friction (FILMMAKER)
- A browser-based approximate 390x844 CSS-pixel inspection (implemented using a same-origin iframe) found no horizontal overflow.
- Mobile nav links occupied only about **15px vertical text/link boxes**; footer email/social anchor boxes about **16px**. This is not necessarily a formal WCAG fail because spacing exceptions matter, but is visibly and ergonomically tight. WCAG 2.2 AA target size guidance is 24x24 or sufficient spacing; 44x44 is an enhanced usability target.
- At widths under 560px, the current `See the work` hero CTA is deliberately hidden by CSS.
- Most important: on touch, first tap prevents navigation and shows a preview, second tap opens the work. Distinct from normal one-tap web navigation.
- **Change proposals requiring visual/interaction approval:** 40-44px nav hit boxes, a subtle mobile cue or button to view work, and one-tap opening or separate explicit preview action.
- **Test:** 320, 375, 390, 428px screens, landscape, VoiceOver, keyboard and touch. The iframe test is not a physical iPhone usability certification.

### Pass 14: CPU, battery and accessibility of motion (FILMMAKER + OVERALL)
- `filmmaker/js/film.js` creates ~24 timecode updates per second, recurring hero switching every 4.2s and touch-card nearest-center updates every 2.5s. The timers are not explicitly gated by document visibility.
- `prefers-reduced-motion` CSS removes transitions/animations but does not stop JS DOM updates.
- **Change:** Pause when hidden, avoid needless timers when components offscreen, honor reduced motion in JS, ensure the initial still remains stable and usable on low-power devices.
- **Acceptance:** Same appearance on supported devices, less offscreen work, no broken touch card interactions. Measure battery/CPU if needed; do not presume a large performance gain.

### Pass 15: Video results, image results and asset discoverability (FILMMAKER + ATHLETE)
- Project pages have user-facing films and posters but no detected VideoObject or video sitemap. Google requires indexable watch pages, stable thumbnails and content prominence for video features, and marks up videos only if they genuinely appear.
- **Potential:** Include suitable VideoObject structured data on genuine project watch pages, optionally video sitemap. Video search visibility is not guaranteed.
- Google Images can surface unique parkour/stunt photos and cinematic stills. Give meaningful stills contextual captions/alt where helpful, not numerical `Still 1` for every frame. Use image-sitemap extensions only if Google has trouble discovering assets.
- Keep video masters hosted reliably: some project pages use remote media sources, so verify poster and video URLs remain publicly fetchable (status, CORS if relevant, range requests, thumbnail permanence).
- Respect intellectual-property and licensing rights for studio film posters, campaign stills and photography; do not add licenses the owner does not hold.

### Pass 16: Keyboard, screen readers and small targets (OVERALL)
- Artist-specific accessible descriptions exist for most images and semantic H1s on project pages; positive.
- The filmmaking landing and root are missing H1. The filmmaker hero displays a large text phrase but it is a `div` of spans, not a heading.
- The custom lightbox has no explicit dialog semantics/focus trap in source. Verify actual screen-reader, tab order and escape behavior.
- Reduced motion and keyboard visibility need real interaction tests, not just static inspection.
- **Change:** Semantic headings without changing visible typography, accessible modal handling and accurate content alt text. Visible hit-area adjustments review separately.

### Pass 17: Identity, off-site authority and evidence (OVERALL / ATHLETE / FILMMAKER)
- Distinct personal brand across athlete and filmmaker is not itself an SEO defect. The larger issue is whether outside portfolio/IMDb/casting profiles and press **link directly to the matching career section** and describe roles consistently.
- Inventory relevant first-party/public profiles: IMDb, production/show credits, verified agency directories, Vimeo/YouTube and social profiles. Keep role wording accurate and link to specific work.
- Investigate brand ambiguity and search results using GSC and real Google results. Generic `site:` queries to public search tools are not proof of indexation.
- Do not buy spammy backlinks or invent awards, endorsements, client results or testimonials.
- **Potential visible change:** A small verified credits/press proof section for each role, when it serves an actual visitor. Do not add indiscriminately.

### Pass 18: SEO to hiring conversion, not just impressions (OVERALL)
- Two separate funnels deserve their own measurement: **athlete/stunt casting enquiries** and **filmmaking/production enquiries**.
- Define success events: clicked email link, opened casting portfolio/reel, meaningful project view, submitted enquiry, qualified enquiry and booked work, when feasible.
- GSC can attribute search query/page impressions and clicks; GA4 can measure consenting visits/actions. Neither alone tells you a signed deal without a way to capture the final outcome.
- **Change:** Distinct hiring cues and direct links to intended landing pages, plus privacy-respecting event analytics.
- On film pages, CTA is currently largely in footer; consider a second unobtrusive contact path after selected projects if data suggests visitors do not reach footer. **VISIBLE proposal**, not implemented.

### Pass 19: Geographic and multilingual hiring intent (OVERALL)
- Audiences include film crews, casting teams and commercial clients in multiple countries, likely including UK and Romania. Avoid claiming a physical base that is no longer accurate.
- Check GSC performance by country and search language before deciding whether to create English/Romanian translations. If translated, build real human-readable equivalents and correct hreflang linking, not machine-generated doorway pages.
- Distinct terms: `stunt performer`, `parkour athlete`, `freerunner`, `acrobat`, `parkour coordinator` versus `Director of Photography`, `commercial filmmaker`, `FPV cinematography`, `colourist`.
- An official coaching qualification or instruction service should be marketed only if actually held/offered. Do not create unverified service pages just for keywords.

### Pass 20: Reprioritization and ongoing QA (OVERALL)
- **Correction to the original audit:** Missing `robots.txt` is not a technical penalty, and a sitemap helps discovery but is not mandatory for 35 well-linked pages. Neither should crowd out a real mobile usability bottleneck or wasted image downloads.
- The most promising quick wins from fresh evidence are **filmmaker initial image loading, mobile card interaction and touch-target sizes**, followed by better H1, page intent and content. Real Google Search Console data still decides search priorities.
- Build repeatable CI checks that parse output pages, not merely source templates. Preserve staging noindex and don't publish `_build`.
- Consider a scheduled lightweight HTML validation and broken-link crawl to catch new regressions, only after confirming hosting/automation costs and crawl courtesy.
- Keep a short change log, baseline metrics, release-by-release comparison and rollback path. Small releases yield clearer evidence than one giant rewrite.

## What was measured and what was NOT

**Observed on live site:** 35 content URLs returned HTTP 200; two root SEO files returned 404; desktop browser network loaded 23 JPG assets totaling approx 4.83 MB encoded content; simulated mobile nav links were ~15px high and footer links ~16px; site code hides mobile hero CTA and requires two taps for first project access.

**Not measured or not authoritative:** user-level Google Search Console impressions/clicks, actual Google-indexed URLs, real phone Core Web Vitals, clean-room cellular LCP/INP, conversion rates, screenshot-diff visual fidelity, network headers across regions, full audit of each asset and all outbound links, real user behavior or official Google Lighthouse scores. The mobile browser check used a simulated iframe and cache, so the reported ~68ms LCP event is **not** a real mobile LCP score; do not quote it as such.

**OpenSEO:** The original report surveyed its free site-audit features but did not run OpenSEO. A comparable bounded live HTTP crawl was executed using Firecrawl. OpenSEO could still supply an independent crawler report and scheduled audit dashboard, but would not replace real PageSpeed/Lighthouse tests or GSC data.
